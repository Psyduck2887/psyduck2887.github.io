这篇文章记录的是我们在公司测试工作中逐步落地的一套 Agent 自动化流程。它不是单独做一个“会跑测试的 Agent”，而是把版本分析、环境准备、任务读取、板端执行、结果整理和消息通知拆成多个可以独立运行的节点，再根据每一步的特点选择脚本、Agent 或人工处理。

目前，组内大约 85％ 的相关流程已经实现自动化，或者已经具备自动化能力。但这里需要区分两件事：已经接入实际工作流的能力，比能够公开、本地模拟的部分更多；Workflow Mock 只复现了其中最核心、最适合演示的一部分。

另一部分能力已经可以单独使用，但仍在逐步接入主线。例如，根据 Gerrit 版本差异决定回归范围，应当发生在核心执行流程之前；长日志分析和自动提单，则位于测试执行之后。

## 1. 已经接入核心工作流的部分

### 1.1 已经接入的整体能力

已经进入实际工作流的内容，不只是在本地能够看到的几个模拟节点。它覆盖了从发现版本、准备环境，到板端执行和结果反馈的一组能力。

| 能力 | 主要作用 | 当前执行方式 | 人工参与 |
|---|---|---|---|
| 发版监测 | 发现新版本并触发后续流程 | 脚本 | 通常不需要 |
| 版本与 SDK 初始化 | 下载、解压并准备不同平台的版本环境 | 脚本为主，异常时 Agent 介入 | 异常时处理 |
| SDK／TestCase／AXP 编译 | 准备测试程序和部分特殊版本产物 | 脚本与 Agent | 异常时处理 |
| Jira 任务读取 | 获取测试单、问题单、步骤和附件 | MCP／接口 | 通常不需要 |
| SOC 烧录与执行 | 把版本和测试产物送到开发板并执行任务 | Agent | 重要异常需要确认 |
| 结果整理 | 保存日志、生成报告并更新测试记录 | 脚本 | 关键结果需要检查 |
| 消息通知 | 同步节点状态和测试结果 | 钉钉通知节点 | 不需要 |

当前消息通知主要使用钉钉。原本也考虑过邮件通知，但 Outlook Webhook 需要管理员开通相关权限，目前没有开放，因此暂时没有接入邮件通知。

这套流程没有把全部工作交给 Agent。输入输出明确、可以稳定重复的步骤优先使用脚本；遇到路径变化、版本差异、编译异常或板端状态变化时，再让 Agent 介入；测试范围确认、最终影响判断等需要负责的决定仍然由人完成。

### 1.2 可以在本地模拟的核心部分

为了公开展示这套方案，我做了一套 Workflow Mock。它不是对真实公司环境的一比一复制，而是保留最核心的输入、状态变化和执行结果，让整条链路可以在本地运行和检查。

本地环境由五个 Docker 实例组成：

| 实例 | 模拟的真实角色 | 主要行为 |
|---|---|---|
| Jenkins | 发版与制品入口 | 模拟发版队列、发现 SDK 链接并控制版本串行处理 |
| Init | 远程编译服务器 | 初始化 SDK，编译 SDK、TestCase 和测试产物 |
| Jira | 任务与附件服务 | 根据测试单或问题单编号返回步骤和任务包 |
| SOC | 开发板 | 模拟烧录、执行测试、校验版本并生成报告 |
| Notify | 单向通知出口 | 模拟节点完成后的消息通知；真实工作主要使用钉钉 |

这套模拟环境承载两条主工作流，它们共用版本初始化、编译和 SOC 执行能力，但任务入口和结果处理不同。

| 工作流 | 任务入口 | 主要过程 | 最终输出 |
|---|---|---|---|
| 问题单验证 | Jira 问题单 | 读取问题描述、步骤和附件，准备环境并在 SOC 上完成验证 | 验证报告和问题处理结果 |
| 固定版本测试 | Test Plan／测试单 | 读取测试任务，准备需要的附件和测试程序，依次执行用例 | Pass／Failed／TBC 结果和版本报告 |

每个节点只通过约定好的输入输出连接，可以单独运行、单独制造异常，也可以由 LangGraph 自动编排。即使上游节点还没有完成，下游也可以使用模拟数据先开发和测试。

## 2. 正在接入核心工作流的部分

### 2.1 从 Gerrit 差异到回归任务

这部分位于核心执行工作流之前。目标是在真正准备环境和执行测试之前，先根据版本改动确定本次需要测试什么。

| 步骤 | 输入 | 处理内容 | 输出 | 当前状态 |
|---|---|---|---|---|
| 版本比较 | Gerrit 前后两个版本 | 分析代码变化及涉及模块 | 改动 JSON | 能力已具备 |
| 回归判断 | 改动 JSON、已有测试单 | 判断 P0／P1／P2 回归等级 | 回归建议 | 正在接入 |
| 模块分析 | 代码改动范围 | 判断受影响模块和建议测试量 | 模块任务列表 | 正在接入 |
| 任务创建 | 模块任务列表 | 创建本次版本测试任务 | Test Plan | 正在接入 |
| 负责人确认 | 自动生成的任务 | 增加或减少任务并记录原因 | 最终测试计划 | 必须人工确认 |

自动生成的计划不会直接成为最终决定。模块负责人仍然可以根据实际情况调整任务；确认完成后，测试计划才进入版本初始化和执行流程。

### 2.2 从长日志分析到问题提单

这部分位于测试执行之后。长日志分析已经可以独立运行，目前正在继续接入结果处理和自动提单。

| 步骤 | 主要处理 | 输出 | 当前状态 |
|---|---|---|---|
| 日志收集 | 保存测试日志和 `/proc` 数据 | 标准日志包 | 已具备 |
| 算法预处理 | 变点检测、模板化、频率统计 | 缩小后的异常候选 | 已具备 |
| Agent 分析 | 结合上下文判断异常并回到原始证据 | 结构化分析报告 | 已具备 |
| 提单信息整理 | 组织版本、步骤、日志位置和异常描述 | 提单 JSON | 正在接入 |
| 自动提单 | 把结构化信息写入问题系统 | 问题单 | 正在接入 |

日志分析节点保持固定输入输出，因此内部算法和模型可以继续调整，不需要同时修改上下游工作流。

### 2.3 保持独立的辅助能力

并不是所有 Agent 能力都需要强行放进版本测试主线。

| 能力 | 用途 | 当前处理方式 |
|---|---|---|
| 客户问题质量分析 | 根据描述、标签、处理过程和结果，筛选值得保留的案例 | 独立运行，结果由人确认 |
| 测试设计辅助 | 整理代码、接口和已有用例，提供测试设计草稿 | 独立运行，必须人工检查 |

测试设计尤其不能直接交给 Agent。即使使用 Claude Fable 5，生成内容仍然更偏向单元测试；面对完整场景、异常组合、边界条件和多模块联动时，可用性仍然不够高。

## 3. 总结：技术之外的落地问题

回头看，这套系统最麻烦的部分并不是技术。2026 年 4 月，我已经完成了核心流程的 Demo 和 MVP，当时虽然还没有完全节点化，但基本功能已经可用。到 2026 年 5 月，主要能力已经拆成独立节点，可以直接接入 LangGraph 编排。

如果只看技术实现，这套方案其实可以更早落地。后来真正消耗时间的，是怎样把它放进现有的工作方式：由谁触发、由谁确认、出现问题后由谁处理，怎样兼容原来的系统和分工，以及怎样让相关人员逐步接受并使用。

这段经历也让我意识到，完成一个技术方案和推动一个项目真正落地，是两种不同的能力。我对 Agent、工作流和工程实现已经积累了一些经验，但在项目实施、协作推动和项目管理方面仍然经验不足。这部分不是再补几个技术节点就能解决的，也是我接下来需要继续学习的内容。

自动化最终要进入真实工作，而不是停留在 Demo 里。技术决定它能不能做出来，项目实施和协作能力决定它能不能被长期使用。
