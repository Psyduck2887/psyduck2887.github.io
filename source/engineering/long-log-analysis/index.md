这个项目解决的是一个很实际的问题：稳定性测试一次可能产生十万行、几十万行，甚至更多日志。人不可能逐行阅读，直接把完整日志交给模型也不现实。

我们的做法不是先问“用哪个模型”，而是先判断日志属于哪一类，再用合适的算法把重复内容压缩掉、把关键数据抽出来，最后才让 Agent 分析真正值得关注的部分。

在当前 SDK 的常见日志上，十万到十五万行通常可以在十分钟左右完成分析，一般不会超过十五分钟。更重要的是，换用不同能力的模型时，最终结果不会出现特别大的差距。

## 1. 三类日志，三种主要处理办法

| 日志特点 | 处理办法 | 主要目的 |
|---|---|---|
| 连续输出编码、帧率等数据，相邻行差别较小 | 变点检测 | 找突然下降、归零和阶段性变化 |
| `/proc` 数据节点按块周期输出，块内内容复杂 | 改进后的模板化 | 保留一份模板和每次变化的数据 |
| 串口和普通文本日志有相似格式，但不依赖连续数值 | 出现频率统计 | 找只出现一两次的少见日志 |

## 2. 连续数据看变化点

稳定性 Demo 运行时，会不断打印编码量、帧率和其他运行数据。这类日志行与行之间通常很接近，真正需要关注的是某个时刻突然发生的变化。

变点检测会先把数据从文本中抽出来，再观察它随时间的变化：

- 数值突然大幅下降。
- 某项指标突然归零。
- 一段时间内持续偏离正常范围。
- 前后两个阶段的表现明显不同。

传统关键词很难发现这类问题，因为日志中未必出现 `error` 或 `fail`。从数值变化入手，反而更容易找到真正影响稳定性的异常。

## 3. `/proc` 数据按块模板化

另一类主要来源是 Linux `/proc` 下各模块的数据节点。系统会定时保存这些节点的内容，通常每秒采集一次。

这类日志相邻两行的差别可能很大，但如果按完整数据块来看，块与块之间往往具有明显的周期和固定结构，因此更适合模板化。

项目借鉴了 Drain3 的思路，但没有直接照搬。普通模板化容易把数字替换成星号，这会让码率、计数、地址和状态值一起消失，后面即使发现模板异常，也很难还原问题。

我们的处理顺序是：

1. 模板化之前先识别并保存关键数据。
2. 把重复的数据块归到同一个模板。
3. 模板只保留一份，每次变化的数据单独保存。
4. 记录模板、变量与原始日志位置之间的对应关系。

对于周期性很强的 `/proc` 日志，压缩率通常可以达到 95％ 以上，同时不会把后面判断需要的数据丢掉。

## 4. 从出现频率里找少见日志

串口日志和普通文本日志不一定包含连续数值，但其中仍然存在大量相似内容。

系统会先把相似日志归为一类，再统计每一类出现了多少次。高频日志通常是正常运行中的固定输出；只出现一次或两次的日志，则更值得优先检查。

低频不等于一定有问题，但它可以帮助 Agent 把注意力放到更小的范围，而不是从几万条重复信息里随机寻找异常。

## 5. 算法处理完，再交给 Agent

三种方法不是互相替代，而是根据日志特点组合使用。实际项目中还有其他处理方式，但变点检测、改进模板化和频率统计是最主要的三类。

Agent 收到的不是完整日志，而是：

- 变化明显的时间段。
- 压缩后的模板和关键变量。
- 少见日志类别。
- 与原始日志行对应的位置。
- 必要的上下文片段。

这样既能减少上下文，也方便 Agent 在给出结论后回到原始证据。

## 6. 两种使用方式

第一种是标准工作流节点。

它接收一个标准日志包，输出一份结构化 JSON 报告。这个接口在多个版本中保持不变，内部算法可以继续调整，上下游不需要跟着修改。

JSON 报告还可以继续交给后面的问题提单节点，把异常描述、原始日志位置和相关数据整理成提单需要的内容。

第二种是独立 Skill。

如果只是临时分析一份日志，或者不需要严格按照完整流程执行，可以让 Pi 等 Agent 直接调用 Skill，自由选择其中的处理工具。只要 Agent 能够正常读取 Skill 结构，就不需要绑定某一种具体模型。

## 7. 模型选择与实际效果

这套流程平时主要使用 DeepSeek V4 Flash。后来它的使用成本上升，截至 2026 年 8 月，近期已经开始换用 GLM-5.3 Flash。

实际使用下来，这套流程对模型并不敏感。因为大规模筛选、重复内容压缩和数据提取已经在前面由算法完成，不同模型拿到的都是比较集中的异常候选。模型能力会影响表达和个别判断，但不会明显改变整体耗时和主要检出结果。

目前公开采用下面这组较保守的数据：

- 十万到十五万行日志通常约十分钟完成，时间波动一般在两分钟左右。
- 常规分析最长控制在十五分钟内。
- 把预算扩展到三十分钟时，可以处理约四十万到五十万行。
- 稳定性问题提单量提升一倍以上。
- 新发现的问题中，约 70％ 来自原先被关键词规则判定为 Pass 的任务。

## 8. 它不是一个通用日志产品

这套方法是根据当前 SDK、日志格式和测试场景逐步调整出来的。换到另一套系统时，变点字段、数据块边界、模板规则和异常判断方式都需要重新适配。

它的通用之处不是“拿来就能分析所有日志”，而是这套分工方式：

```text
先看日志特点
→ 用算法减少重复内容
→ 保留原始位置
→ 再让 Agent 做理解和判断
```

当前页面只使用脱敏后的方法和结果，不包含真实日志、问题单内容和内部测试数据。
