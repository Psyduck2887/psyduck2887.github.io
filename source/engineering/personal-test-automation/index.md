我主要负责 SYS、VO、MIPI TX 和 MIPI RX 等模块的测试。过去，这些工作需要手动跟进发版、准备十几个 AXP 包、编译测试程序、烧录开发板、执行测试、查看日志，再整理测试记录和问题单。

2025 年 10 月左右开始接触 Code Agent 后，我逐步把这些重复工作拆成脚本和独立节点，并让常态运行的 Pi Agent 只在异常发生时介入。目前，除了测试设计、最终判断和跨团队沟通之外，我个人负责的测试流程大约有 90％ 已经实现自动化。

## 1. 没有使用 Agent 自动化之前的工作流

早期使用 AI 时，我主要是在外部网页上提问，让它帮助分析问题或编写一部分代码。AI 能减少单次编码的时间，但没有真正进入测试环境，版本准备、服务器编译和板端执行仍然需要人工完成。

### 1.1 原来的执行顺序

一个版本发布后，原来的工作大致是：

```text
人工查看发版
→ 准备并修改十几个 AXP 包
→ 编译测试用例可执行文件
→ 烧录开发板并执行测试
→ 查看日志与运行结果
→ 整理测试记录和报告
→ 准备并提交问题单
```

### 1.2 手工流程的问题

这些步骤本身并不复杂，但数量多、持续时间长，而且容易受到版本、路径、参数和环境状态变化的影响。一处准备错误，往往要到板端执行时才会暴露；发现问题后，还需要重新检查前面的每一步。

主要问题可以归为三类：

- **重复准备较多**：每个版本都要重新处理包、程序、路径和板端环境。
- **问题暴露较晚**：前面一处配置错误，可能到烧录或执行时才会发现。
- **信息比较分散**：发版记录、编译输出、开发板日志、测试单和问题单需要人工来回整理。

## 2. 使用 Agent 自动化之后的工作流

从 2025 年 10 月左右开始使用 Code Agent 后，我先把输入输出稳定的步骤写成脚本，再把各步骤拆成可以单独执行和检查的节点。现在的流程大致是：

### 2.1 自动化后的执行顺序

```text
自动监测版本
→ 按模块准备并编译 AXP 包
→ 编译对应版本的测试程序
→ 自动烧录并执行测试
→ 保存日志、报告和测试记录
→ 整理问题证据与提单内容
```

正常情况下，整条流程由脚本推进。脚本速度快、结果稳定，也方便判断某一步是否按预期完成。Agent 不需要每次从头接管，而是在节点异常时才被唤醒。

### 2.2 异常出现时再唤醒 Agent

服务器上常态运行着一个基于 Pi 的 Agent。某个节点没有正常完成时，它会检查路径是否变化、版本结构是否调整、包和依赖是否完整、编译参数是否兼容，以及节点输出是否符合原来的约定。

Agent 的处理范围有明确限制：

- 每次处理都有时间或尝试次数限制，不会无限循环。
- 修复完成后先保留旧节点，再安装和验证新节点。
- 新节点通过检查后，工作流才继续执行。
- 在限制范围内没有解决，就停止处理并保留现场，交给人工查看。

这种做法让 Agent 负责处理重复流程中的意外变化，又不会让它在失败时不断扩大修改范围。

### 2.3 仍然需要人完成的工作

仍然需要由人完成的工作主要有三类：

1. **测试设计**

   经过几个月实际使用，我仍然不认为 Agent 可以独立完成可用性足够高的测试设计。即使使用 Claude Fable 5，它生成的内容也更偏向单元测试；面对完整业务场景、异常路径、边界条件和多模块组合时，考虑往往不够完整。因此，Agent 可以整理代码和已有用例，也可以提供草稿，但测试设计必须由人检查和调整。

2. **跨团队沟通**

   与开发、前线、产品和其他团队确认问题，涉及背景、责任和真实影响。Agent 可以帮助整理信息，但不能代替人完成沟通。

3. **最终影响判断**

   日志波动、测试失败和用户影响并不是一回事。是否需要中断测试、拦截版本或提交问题单，仍然要由测试人员负责。

## 3. 总结

从在网页上向 AI 提问，到真正把 Code Agent 接进服务器和开发板，我对自动化的理解也发生了变化。真正有用的不是让 Agent 一直操作所有东西，而是先把稳定流程交给脚本，再让 Agent 处理节点之间难以预料的变化。

目前约 90％ 的个人测试流程已经可以自动推进。省下来的主要是版本准备、编译、烧录、执行、记录和材料整理的时间；测试设计、异常判断和沟通仍然由人完成。这种分工没有追求完全无人参与，但更适合长期使用。
